# 逐封審核核心

依 [系統架構](https://app.notion.com/p/3f42685d1879816e8378dd53a127cb8b) 與
[審核佇列任務](https://app.notion.com/p/3fb2685d1879810caed3f4a1c9b57020)，
先完成單封草稿送審、人工核准與修改後失效的離線邏輯。未接上資料庫、API、頁面或 Gmail。

## 資料與操作

從 `lib/mail-review/index.ts` 匯入三個函式：

| 函式 | 用途 |
| --- | --- |
| `submitForReview(draft, actor, submittedAt)` | 建立 `pending_review` 紀錄，保存送審人、時間及完整快照 |
| `approveReview(review, currentDraft, actor, approvedAt)` | 核准仍與送審快照一致的單封草稿，記錄核准人、時間與草稿版本 |
| `reconcileReview(review, currentDraft)` | 重新核對目前草稿；有變更時回傳 `invalidated`，保留原快照與舊核准供追溯 |

操作成功回傳 `{ ok: true, review }`；失敗回傳 `{ ok: false, code, message }`。
失敗結果不包含完整信件、收件人、附件內容或原始例外，也不產生部分核准。

`ReviewDraft` 沿用 `lib/pre-send` 的 `StructuredDraft`，加上 `clubId`、`subject`、`body`。
上一步的 `GeneratedDraft` 只有生成的文字，呼叫端須先從可信資料來源組裝完整草稿，
帶入草稿 ID、新版本、社團、To／Cc／Bcc、窗口、廠商、活動、附件與連結後才送審。
沒有 Cc／Bcc、附件或連結時明確傳入 `[]`，不可省略結構。

快照保存所有已知欄位並深層複製、凍結；不採用輸入額外附加的 `approved`、`canSend` 等旗標。
主旨不可換行，主旨與內文不可空白。其餘僅做快照結構核對；收件人、活動基準、
附件需求、實際檔案內容與連結存取等仍須在寄前檢核及人工審核流程確認。

## 核准失效與重審

- 版本、收件人、主旨、內文、窗口、廠商、活動、附件參照／版本或連結資源版本
  有任何變更，都須重新送審。即使呼叫端漏改版本號，內容差異仍會讓核准失效。
- 文字不去空白、不改大小寫；清單順序也精確比較。活動額外欄位僅調換物件 key 順序，
  不視為內容修改。
- 待審核紀錄修改後同樣失效，避免審核者看見的版本與後端核准的版本不同。
- `invalidated` 紀錄維持失效，改回舊內容也不會復活。用目前草稿重新呼叫
  `submitForReview`，產生新紀錄後才能核准；舊紀錄須由資料存取層保留。
- 不同草稿 ID 或不同社團的紀錄不能互相套用。同一封已核准紀錄再次核准會回報狀態錯誤。

**接線時，每次編輯必須產生未用過的新 revision，並保存失效狀態。**
若編輯後又還原文字，不能重用舊 revision。純函式只看得到傳入的當下資料，
無法察覺呼叫端漏存的中間修改；不能只看資料庫舊紀錄的 `status: approved` 就寄送。
載入狀態、編輯與寄送前都須重新核對目前草稿，避免拿舊版本的核准套在新版本上。

## 身分、時間與後續整合

`ReviewActor` 的 `id`、`clubId`、`canSubmitForReview`、`canApprove`，
必須由伺服器驗證 session 與該社團操作權限後提供；不能採用前端自報的核准權限。
本核心檢查社團與明確的能力值，不另行決定哪些角色具有審核權，避免改動 Liana 的權限設計。
審核紀錄也必須由可信的資料存取層載入，不能接受請求 body 裡自製的已核准物件。

時間由後端提供，沿用既有 `parseInstant` 驗證含秒與時區的 ISO 時間；
核准時間不能早於送審時間。不自行制定核准到期日或自審限制。

`approved` 只代表本次單封人工審核紀錄成立，**不等於已完成所有寄前檢核或允許直接寄出**。
未來寄送端仍須重新驗證登入／社團／寄送權限、目前版本、完整寄前檢核及每日額度，
並以資料庫交易或等效機制處理版本競爭、核准失效、額度保留、寄送重入與狀態保存。
附件版本及連結資源版本應由可信來源取得，不能只依使用者填寫的檔名或版本文字判斷內容未變。
本階段沒有寄送入口、持久化、審核歷史查詢、退回修改或批次核准功能。

測試全部使用虛構資料及固定時間，不讀環境變數或 `.env.local`，不呼叫 AI 或 Google。
